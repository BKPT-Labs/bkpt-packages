BKPT STM32G5 PLAY capability policy, version 1. SPDX-License-Identifier: LicenseRef-BKPT-Proprietary. Each numbered line is one rule and is cited by its line number. A rule is a BKPT decision, not a manufacturer statement.
1. Inventory: pins, signal routes and interrupts are transcribed from the pinout descriptor, device header and startup vector table the graph pins; a route records what is declared, not that a capability may use it.
2. PLAY sub-resources: PLAY1 is recorded as 16 input multiplexers, 16 lookup tables, 16 output multiplexers and 16 software triggers, each its own exclusive resource, from the SDK enumerators that name them; the counts are those enumerators, not a reading of the reference manual.
3. PLAY pad routes: an input multiplexer INn is joined to a pad only where the pinout descriptor declares signal PLAY1_INn on that pad, and an output multiplexer OUTn only where it declares PLAY1_OUTn; the route carries the descriptor's alternate function.
4. Board pads: on the NUCLEO-G564RE a PLAY pad is allowed only when the board composition of the captured board project connects no board part to its package position; the user button B1 position is allowed for PLAY inputs only; the board netlist further restricts allocation to exposed header nets with only unmounted bridges, or the PC13 button input through SB5; pads with the debug probe, the virtual COM port, the user LED or a crystal are never allowed.
5. Ownership: every generated PLAY unit holds PLAY1 in ownership mode bkpt_play_units and owns its input multiplexers, lookup table, output multiplexer, software trigger and pads exclusively; nothing else may configure PLAY1 in the same application.
6. Kernel clock: the first PLAY unit resets the entire owned PLAY1 block once, enables LSI, selects LSI as PLAY1 kernel clock with divider 1, as the four HAL PLAY examples of STM32CubeG5 2.0.0 for this board do; later units check that selection and do not change it.
7. Truth tables: a function is written as the 16-bit truth table that the SDK's documented formula gives with input A on lookup table input 0 and input B on input 1; unused inputs 2 and 3 keep the SDK default source and every listed table is independent of them.
8. Configuration order: input pads are set to the PLAY alternate function before the PLAY input is configured; the output pad is connected only after PLAY1 is started, as the SDK's usage text orders it.
9. Shared start: a unit stops PLAY1 when it is already started, writes only its own multiplexers and lookup table, starts PLAY1 again with no edge trigger and reads back what it wrote; while it does, every other unit's kernel-clock features are held in reset, so all units are initialized before outputs are relied on.
10. Integration: the units switch on the SDK's PLAY and GPIO modules and add the CMSIS components the STM32CubeG5 PLAY examples list for them, pinned to the exact foundation files they edit.
11. Claims: no timing, latency, glitch, electrical, filter accuracy or hardware behavior is claimed; a unit's run-time checks read back registers through SDK getters and are not measurements.
